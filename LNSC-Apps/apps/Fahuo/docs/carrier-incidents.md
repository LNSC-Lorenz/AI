>
> 2026-10-24 清理前引用的八个 `_sf_*` / `_sb_*` 真单探针已删除。下文保留其名称仅说明历史证据来源，**不可直接复现**。完整原始上下文见 `archive/0_README-2026-10-24.md`。

## 1. 承运商客户单号复用导致撞单

**现象**：新订单得到旧运单或他方运单，预览数据与官方 PDF 内容不一致。

**根因**：曾把 DN、数据库自增 ID 或会被重置的本地序号当作顺丰 `orderId`。承运商按客户单号幂等，客户单号注册历史不会因本地清库而消失。

**永久防线**：

- DN 只用于平台内部，不下发承运商。
- 顺丰 `orderId`、德邦 `custOrderNo` 统一由 `next_oid()` 分配。
- `oid.seq` 每环境独立持久保存，清库、删单、取消和部署都不得重置或复用。
- 撞单排查先比较 `order_resp.order_id` 与当前 `oid.seq`，再排查面单模板。

## 2. 顺丰产品与回单参数误判

### 产品映射

历史撞单和近线降级曾污染产品判断。当前已确认：`expressTypeId=1` 为特快，`2` 为标快；近线无特快时可能降级，不能据此反推映射。`routeLabelInfo.expressTypeCode` 不用于判断实际产品，`proCode` / `limitTypeCode` 才反映执行产品。

历史证据 `_sf_type12_contrast.py` 已删除；现行映射以代码和 README 为准。

### 回单与拍照回传

`isSignBack=2/3` 虽可能被网关接受，却曾出现运营端没有有效回单任务的情况。`extraInfoList attrCode POD` 也不是可用替代通道。

当前防线：纸质回单只发 `isSignBack=1`；拍照回传只发 `serviceList IN91/value=13`；纸质回单不额外发 IN03。`waybillType=3` 是回单运单，不计入主/子件件数。

历史证据 `_sf_signback_route_probe.py`、`_sf_signback3_probe.py`、`_sf_in91_probe.py` 已删除。

### 回签单面单

曾把 SF106 回单号放入 `masterWaybillNo`，得到正向 POD 签收联，导致方案多次启用和撤回。当前唯一有效口径是 `documents[].backWaybillNo`，打印签回单时主/子运单字段为空；追加失败不阻塞主面单。

历史证据 `_sb_back_probe.py`、`_sb_pages.py` 已删除。旧 `optional_no + with_optional=1` 仅作兼容，不作为新功能入口。

## 3. 顺丰路由 20028 被误显示为“待揽收”

**根因**：到付等订单缺少收/寄方手机号后四位校验，或误用短参数 `checkNo`，承运商返回 20028；平台又把空路由统一显示为“待揽收”，掩盖真实错误。

**永久防线**：所有顺丰路由请求使用长名 `checkPhoneNo`；收件电话优先、员工寄件电话兜底；空路由显示 `reasonRemark`，不得盲显“待揽收”。

## 4. 德邦取消、轨迹和面单的易错点

- 下单后异步入账存在延迟，立即取消可能报订单不存在；保留退避重试。
- 轨迹只认 `mailNo + customerCode`，不要改用 `waybillNo(s)`。
- 面单 `queryBillPrint` 的 `customerCode` 必须是客户编码，不是公司编码。
- 面单异步生成，短时间查询不到不等于无权限；不得因此回退到非官方 HTML 面单。
- 纸质回单必须放在 `addServices.backSignBill / returnRequirement / returnBillQty` 内；放顶层会被静默忽略。德邦没有顺丰式 type=3 回单运单追踪，也不能套用 IN91。
- `logisticID` 每单消耗一个，序列文件不得复用或重置。

## 5. A1004 权限误判

`A1004` 不一定都是服务未订阅。历史探针经 bash 读取 CRLF 环境文件时，`partnerID` 尾部的 `\r` 污染签名，也会产生 A1004。生产 systemd 注入未受此问题影响。

排查顺序：先确认环境值已 strip、无 CRLF 污染，再判断服务权限；下单、路由、云打印权限分别开通，不能以一个接口推断其他接口。

## 6. 回单返回地址与人工确认

历史误投的账号侧到方地址已维护并结案，平台不再保留地址维护接口、申请文案或历史单号。回单运单终态不等于实物已经回到莱克勒：`SIGN_BACK_MANUAL_SINCE` 之后的新单只提示并记录回单轨迹，人工核实实物后才能置 `returned`；此前历史单保持原逻辑，不回溯。

## 7. webroot 清理与安全边界

历史误删证明：`/var/www/lnsc-apps/apps/fahuo` 不是可任意清空的独立目录，`label/` 是生产运行内容，`ShippingPhotos/` 是共享盘挂载点。任何清理必须先核对挂载、运行进程和部署清单，禁止递归强制删除整个应用目录。

当前防线：密钥和数据库不入库、运行时资料部署排除、webroot 拦截源码/密钥/库文件。历史提交中的旧承运商密钥是否完成轮换、`.csv` 是否也需要拦截，仍列在 README 未决事项中，未确认前不得视为已关闭。

## 8. 顺丰 20023「暂无路由信息」被误判为已揽收（2026-10-26）

**现象**：2026-10-26 多张当天顺丰单已下单、尚未揽收，下单页无法进入「取消下单」，直接调用取消接口也被拒绝（当前路由状态：暂无路由信息）。

**根因**：顺丰 `EXP_RECE_SEARCH_ROUTES` 对新单（尚无揽收扫描）固定返回 `reasonCode=20023`、`reasonRemark=暂无路由信息`、`routes=[]`。2026-10-24 为暴露 20028 改成“空路由以 `reasonRemark` 为状态”后，20023 被原样写入 `route_status`；而取消闸门、看板“已发货”和清单发货判定都只认 `route_status != 待揽收`，于是未揽收单被当成已发货且不可取消。

**证据**：生产 7 张当天单数据库 `route_status=暂无路由信息`，`GET /api/carrier/route` 逐一返回 `route_reason_code=20023`、`detail=[]`；用户确认均未揽收。

**当前修复**：`carriers/sf_express.py` 将 20023 /「暂无路由信息」归一为「待揽收」，20028 等其他 `reasonRemark` 继续原样暴露；`server.py` 取消闸门接受「待揽收/暂无路由信息」，并在启动时把历史 `route_status='暂无路由信息'` 幂等归位；下单页按钮按同一口径启用取消。

**永久防线**：只有 20023 可以视为“尚无揽收扫描”；其余空路由原因必须保留原文，不能因为修取消而重新把 20028 等错误显示为“待揽收”。

**验证**：部署后路由接口对上述 7 单返回 `route_status=待揽收` 且保留 `route_reason_code=20023`，数据库历史行已归位，下单页选中该行显示「取消下单」；未实际取消任何真实运单。

**文档**：README「取消与路由共同规则」「顺丰：主运单路由」。
