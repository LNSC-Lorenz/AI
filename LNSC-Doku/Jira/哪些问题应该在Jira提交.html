Jira 问题提单标准

Issue Logging Standards — When and What to Submit in Jira

为规范研发问题与需求的管理，确保工作项可追踪、可复盘、不遗漏，现就“哪些问题应提交至 Jira”统一规定如下，请全体相关人员遵照执行。

发布日期2026-10-25生效日期2026-10-25

一、应提交至 Jira 的问题

1
缺陷（Bug）：功能报错、崩溃、数据错误、界面异常、与需求/设计不符的行为。须可复现，记录步骤与结果。
2
新需求 / 功能改进：新增功能、体验优化、性能提升、可维护性改进。须描述目标与验收标准。
3
任务（Task）：技术改造、接口联调、部署发布、环境配置、依赖升级等需排期的工作项。
4
线上 / 生产事故：任何影响用户或系统可用性的故障，无论是否已定位，须立即建单并标记 Blocker。
5
跨团队协作项：需多团队/多角色分工、有明确交接与截止时间的事项。

二、一般无需提交至 Jira 的问题

  • 个人使用咨询：如“某按钮位置”“如何登录”等，走 IM（Teams/微信）或文档即可。
  • 临时、一次性且不涉及改动：如确认信息、临时查数，无交付物。
  • 可当场解决且无需追踪的口头小疑问：10 分钟内闭环、无后续动作的沟通。
  • 重复单：已有相同 Issue 时，应评论/关联，而非新建。

三、视情况提交的边界问题

!
轻微体验问题（低优先级 UI / 文案）：若影响用户或需统一修复，建议建单为 Minor 并入需求池。
!
待确认的技术疑点：暂无法确定是否为缺陷时，先建单标记 待验证，避免遗漏。
!
跨项目依赖：本项目动作依赖外部交付时，建单并建立 blocks / is related to 关联。

四、判断速查表

问题特征是否建单说明
功能不可用 / 报错 / 数据错误必须建 Bug，附复现步骤与截图
影响生产 / 用户必须建 Incident/Blocker，第一时间建单
新增 / 改进需求必须建 Story，写清验收标准
需排期或多人协作必须建 Task，指派并定优先级
轻微体验 / 待确认疑点建议建单但标低优先级，避免遗漏
个人咨询 / 一次性沟通不建走 IM 或文档即可
已有相同 Issue不建评论或关联已有单

五、提交前自检清单

  • 是否已有相同 Issue？（先搜索，避免重复建单）
  • 标题（Summary）是否一句话能说清问题？
  • 描述是否包含：现象 / 期望 / 实际 / 复现步骤 / 环境？
  • Issue Type（Story / Bug / Task）与 Priority 是否正确？
  • Assignee、Sprint、关联项目是否已填写？
  • 是否附了必要的截图 / 日志 / 链接？

原则提示：拿不准该不该建单时，倾向于建单——宁可多建一条被评审剔除，也不要漏掉一个需要追踪的问题。
